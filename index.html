What does this tool do?

This tool answers one question: what can a specific user do on a specific record? Upload the security spreadsheet for your Odessa system (or use the demo), tell us who the user is and what you're checking — and we'll show you the answer in plain English.

New to the terminology? Open the Glossary below, or hover the ? markers next to any label.

Glossary — what do these terms mean?
F — Full
The user can see, edit, and do everything on this record.
M — Modify
The user can open and edit the record, but special admin actions are hidden.
R — Read
The user can open and view the record but cannot change anything.
N — None
The record is completely hidden from this user — they cannot access it at all.
X — Not set / undefined
"No specific rule here." The system keeps looking. If nothing ever resolves, it acts like None.
Record type / Block
A category of record in Odessa — e.g. Invoice, CreditMemo, PostInvoice. Each has its own permission rules in the spreadsheet.
Operation / Field
A specific action or field on the record — e.g. Amount, ApprovedBy. Leave blank to check access to the record itself.
Role
A label assigned to a user that determines what they can do. A user can have multiple roles.
Default permission
The fallback access level for a role — used when no specific rule matches. Set per role in the database.
System fallback
A site-wide setting that fills in for any role whose default is "not set" (X). Usually Full.
Record property / Condition
A fact about the specific record being accessed (e.g. "Is this invoice active?"). Some rules only apply when the record has a certain property.

Step 3 · user roles Step 3 · Who is the user?

DefaultPermission is the value that role carries on the master Roles entity in the database. If it is X, the framework substitutes the site-level default at login time (why?).

Each role has a general access level stored in the database. If it's set to X (not set), the system uses the system fallback permission you chose above.

UserContextHelper.cs reads Global.UserRole.DefaultRolePermission when building the user's role list. Any role whose stored DefaultPermission is X is rewritten to that site-level value before the cascade ever runs — so step 5 in production never sees X.
